# Multi-Agent Company Bench：第一版六场景设计

> 状态：场景目录设计，不包含代码实现。

## 1. 第一版只使用两个分类维度

一个场景只由两件事定义：

```text
场景身份 = 企业关系拓扑 + 商品的主导物理特性
```

### 1.1 企业关系拓扑

| 拓扑 | 通俗解释 | 最简单的结构 |
|---|---|---|
| 线性链 | 商品沿着一条主路径逐层向下游流动 | 原料商 → 加工商 → 零售商 |
| 汇聚 BOM-DAG | 多种互补投入必须汇聚后，才能形成一个产出 | 芯片 + 电池 → 设备 |
| 双边平台 | 平台连接两类企业，核心问题是匹配供需双方 | 货主 ↔ 平台 ↔ 承运商 |

`BOM` 是 Bill of Materials，即“物料清单”；`DAG` 是没有循环的有向图。
“汇聚 BOM-DAG”在第一版里只需理解为：缺少任何一种关键投入，生产就无法完成。

### 1.2 商品的主导物理特性

| 特性 | 通俗解释 | 最主要的经营问题 |
|---|---|---|
| 易腐 | 放久了就会失去价值 | 缺货与浪费之间的平衡 |
| 耐储 | 可以跨期保存 | 现金被库存占用 |
| 可转化 | 投入经过加工变成另一种商品 | 原料配比、产能和加工成本 |
| 纯产能 | 卖的不是库存商品，而是某一时期的服务能力 | 当期不用就永久消失 |
| 不可分项目 | 必须凑齐全部条件才能获得收益 | 做成才有收益，半成品几乎无价值 |

这些特性不是互斥的。例如鲜奶既“易腐”又“可转化”。为了保持分类简单，
每个场景只选择一个最能决定经营难点的“主导特性”，其他特性只是场景参数。

## 2. 其他机制放进统一配置

协调方式、不确定性、信息结构和外部性不再定义新的场景家族，而是同一场景的配置：

```text
MechanismConfig
├── market_mode          # spot / contract / auction
├── demand_volatility    # 需求波动强度
├── supply_volatility    # 供给波动强度
├── information_delay    # 信息延迟期数
├── credit_enabled       # 是否允许赊账
├── waste_penalty        # 浪费惩罚
└── fairness_threshold   # 最低公平要求
```

其中：

- `demand_volatility` 这类连续数值是真正的超参数；
- `market_mode` 这类选项是配置开关；
- 第一版固定使用现货交易、即时付款、轻微需求波动、无信用、无谈判。

这样可以先比较场景本身，避免同时改变太多机制而无法解释结果。

## 3. 六个场景的总体布局

六个场景不是随机选择的六个行业，而是三个“对照组”。每组保持企业拓扑相同，
只改变主导物理特性。

| 对照组 | 场景 | 企业拓扑 | 主导物理特性 | 最核心的决策难题 |
|---|---|---|---|---|
| 线性链 A | 鲜牛奶 | 线性链 | 易腐 | 多生产会浪费，少生产会缺货 |
| 线性链 B | 基础服装 | 线性链 | 耐储 | 库存不会坏，但会占用现金 |
| BOM A | 简化电子设备 | 汇聚 BOM-DAG | 可转化 | 任一关键零件短缺都会卡住装配 |
| BOM B | 小型工程项目 | 汇聚 BOM-DAG | 不可分项目 | 只有完整交付项目才能获得收入 |
| 平台 A | 公路货运平台 | 双边平台 | 纯产能 | 未使用的当日运力无法留到明天 |
| 平台 B | 二手工业设备平台 | 双边平台 | 耐储 | 商品可以等待，但买卖双方可能长期错配 |

## 4. 场景一：鲜牛奶

### 定位

```text
线性链 × 易腐
```

### 最小参与者

- 2 家牧场；
- 2 家乳品加工厂；
- 2 家零售商；
- 消费者由环境模拟，不是 Agent。

### 最小商品流

```text
牧场生产原奶
→ 加工厂购买原奶
→ 原奶加工为盒装奶
→ 零售商购买盒装奶
→ 消费者购买
```

### 第一版只保留的决策

- 牧场：生产多少、卖多少、最低售价；
- 加工厂：买多少、最高买价、加工多少、盒装奶最低售价；
- 零售商：买多少、最高买价、零售价。

### 物理规则

- 原奶保质期短；
- 盒装奶保质期稍长；
- 过期库存价值归零；
- 原奶按照固定比例转化为盒装奶。

### 为什么适合作为第一个 MVP

它同时具备上下游合作、同层竞争、库存、加工和浪费，但仍然只有一条主链，
可以用最少规则跑通完整企业经营闭环。

## 5. 场景二：基础服装

### 定位

```text
线性链 × 耐储
```

### 最小参与者

- 2 家布料供应商；
- 2 家服装加工厂；
- 2 家零售商；
- 消费者由环境模拟。

### 最小商品流

```text
布料 → 基础款成衣 → 零售
```

第一版只生产一种基础款服装，不加入尺码、颜色、潮流和退货。

### 与鲜奶场景的关键区别

- 布料和成衣不会在几天内过期；
- 未售库存可以留到下一期；
- 但库存会占用现金，并产生小额保管成本；
- 企业因此可以囤货，却不能无限囤货。

### 研究价值

它与鲜奶拥有几乎相同的企业拓扑和行动空间。二者表现差异主要来自
“易腐”与“耐储”，因此最适合做一组干净的对照实验。

## 6. 场景三：简化电子设备

### 定位

```text
汇聚 BOM-DAG × 可转化
```

### 最小参与者

- 2 家芯片供应商；
- 2 家电池供应商；
- 2 家设备装配商；
- 2 家零售商。

### 最小 BOM

```text
1 个芯片 + 1 个电池 → 1 台设备
```

屏幕、外壳、物流和质量等级暂时不进入第一版。

### 最小决策

- 零件供应商：产量、报价；
- 装配商：两类零件的采购量、采购价、装配量、销售价；
- 零售商：采购量、采购价、零售价。

### 核心难题

芯片和电池是互补品。即使装配商有大量芯片，只要缺少电池，就无法生产设备。
这个场景测试 Agent 能否协调多种投入，而不只是沿一条链补货。

## 7. 场景四：小型工程项目

### 定位

```text
汇聚 BOM-DAG × 不可分项目
```

### 最小参与者

- 2 家水泥供应商；
- 2 家钢材供应商；
- 2 家工程承包商；
- 项目需求由环境发布。

### 最小项目

```text
10 单位水泥 + 5 单位钢材 + 1 单位承包产能
→ 1 个已交付项目
```

### 第一版规则

- 每期环境发布若干同规格项目；
- 承包商只有凑齐完整投入并交付，才能获得项目收入；
- 不完整的投入可以留存，但“半个项目”没有收入；
- 第一版不加入长期工期、分包、质量验收和违约诉讼。

### 与电子设备场景的关键区别

电子设备可以一台一台连续生产；工程项目则强调全有或全无。
这个场景测试 Agent 是否会在承诺项目之前确认所有关键资源。

## 8. 场景五：公路货运平台

### 定位

```text
双边平台 × 纯产能
```

### 最小参与者

- 3 家货主企业；
- 3 家承运企业；
- 平台由环境运行，第一版不是 Agent。

### 最小交易

```text
货主提交运输需求和最高愿付价格
↔ 平台撮合
↔ 承运商提交当日运力和最低接受价格
```

第一版把所有线路视为同一种标准运输任务，不加入地图和路径规划。

### 物理规则

- 每家承运商每天拥有一定数量的运输槽位；
- 当日未出售的槽位不能储存到下一日；
- 未被满足的货运需求产生延迟成本。

### 核心难题

双方都需要预测当日供需并报价。价格太高会闲置运力，价格太低又可能无利可图。
这个场景用很少的对象体现平台匹配和“产能会过期”。

## 9. 场景六：二手工业设备平台

### 定位

```text
双边平台 × 耐储
```

### 最小参与者

- 3 家设备出售企业；
- 3 家设备采购企业；
- 平台由环境运行。

### 最小交易

```text
卖方发布设备和最低售价
↔ 平台撮合
↔ 买方提交最高报价
```

第一版中，设备价值和状态全部公开，不加入欺诈、质量私有信息和复杂议价。

### 物理规则

- 未成交设备可以继续保留和挂牌；
- 每台设备按整数单位成交，不拆分出售；
- 持有设备会产生少量保管成本；
- 买方购得设备后获得固定的经营价值。

### 与货运平台的关键区别

货运槽位今天不用就消失，设备今天卖不掉还可以明天再卖。
这组对照可以直接检验“不可储存的产能”和“可储存的资产”如何改变报价与匹配策略。

## 10. 第一版的统一默认机制

为了让六个场景可以比较，V1 统一采用：

| 配置 | 默认值 |
|---|---|
| 交易方式 | 集中式现货撮合 |
| 结算方式 | 成交后立即现金结算 |
| 决策频率 | 每家企业每期决策一次 |
| 信息 | 自身现金和库存私有，历史成交价公开 |
| 不确定性 | 只有轻微、可复现的需求波动 |
| 信用与负债 | 关闭 |
| 自由文本谈判 | 关闭 |
| 运输过程 | 省略，成交后立即交付 |
| 运行期数 | 30 期 |

在所有企业提交决策后，环境再统一结算，不能让响应更快的 Agent 获得先手优势。

## 11. 推荐的简化场景 ID

第一版不把波动、信用和规模全部塞进 ID。ID 只表达场景的稳定身份：

```text
<topology>.<industry>.<dominant_physics>.v<version>
```

六个场景分别为：

```text
chain.dairy.perishable.v1
chain.apparel.storable.v1
bom.electronics.transformable.v1
bom.construction.indivisible.v1
platform.freight.capacity.v1
platform.equipment.storable.v1
```

企业数量、随机种子和机制参数放在运行配置中。例如：

```text
scenario_id = chain.dairy.perishable.v1
seed = 42
demand_volatility = 0.10
information_delay = 1
```

## 12. 推荐实现顺序

1. 鲜牛奶：建立最小经济引擎；
2. 基础服装：验证同一线性链能否仅替换物理参数；
3. 公路货运平台：加入最简单的双边撮合；
4. 简化电子设备：加入多投入 BOM；
5. 二手工业设备平台：验证平台中的跨期库存；
6. 小型工程项目：最后加入全有或全无的项目收益。

这个顺序不是按行业重要性排序，而是按新增机制的工程难度递增。

## 13. 最终建议

第一版不要定义“行业基类”和六套独立 Engine。应先把六个场景看成：

```text
少量稳定拓扑
+ 少量商品物理规则
+ 一份可调的 MechanismConfig
```

只有当第二种真实实现出现后，再抽取新的 Interface。例如：

- 只有现货撮合时，不创建 `BaseMarket`；
- 加入拍卖后，再从两种真实结算方式中抽取市场 Interface；
- 只有鲜奶时，不创建 `BaseIndustryScenario`；
- 服装场景跑通后，再抽取两者真正共享的线性链配置。

这样既保留后续扩展空间，也不会让第一版被大量抽象类和配置项淹没。
