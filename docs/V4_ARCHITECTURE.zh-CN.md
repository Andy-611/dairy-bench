# V4 架构与不变量

## 目标

V4 模拟九家独立企业在连续乳制品现货市场中的经营。它引入可信的日内价格发现和
物理提前期，同时保持 Benchmark 确定、可审计且足够简洁。

当前场景为 `flow.dairy.base.s9.v5`：

- 三家牧场生产原奶；
- 三家加工厂购买原奶、加工并出售盒装奶；
- 三家零售商购买盒装奶、设置零售价并服务消费者。

V2 文档作为历史行为保留；V4 不保留旧版兼容 Adapter。

## 模块边界

```text
CompanyAgent
    | 一条强类型命令
    v
EpisodeRuntime ---- Scheduler
    | 确定性批次顺序
    v
EconomyEngine ---- ContinuousSpotMarket ---- AssetLedger
    | 强类型状态与事件
    v
LifecycleRepository ---- Journal + Checkpoint + SQLite
    |
    `---- Evaluator / Timeline / Replay
```

各模块职责刻意保持单一：

- `CompanyAgent` 只选择一条已授权 `CompanyCommand`，不能修改状态。
- `EpisodeRuntime` 负责虚拟时间、唤醒、并发推理、由 seed 决定的应用顺序、Journal
  序号和 Checkpoint 边界。
- `EconomyEngine` 负责业务授权、物理作业、到货、消费者结算、库存过期和强类型投影。
- `ContinuousSpotMarket` 负责单一商品的目标报价阶梯原子对账、资产冻结、价时撮合、
  部分成交和关市。
- `AssetLedger` 是一次事务中可用现金和 FEFO 库存的唯一权威；两个商品市场在同一
  引擎事务内共享 Ledger。
- `LifecycleRepository` 原子持久化新增 Journal 和替换后的 Checkpoint；各种投影
  不成为第二份事实源。

边界状态使用不可变 Pydantic 模型。撮合所需的可变操作仅存在于短生命周期的事务内
Market Session，返回前重新冻结为 `EconomyState`。

## 每日事件顺序

企业命令窗口为 `[09:00, 19:00)`：

| 时间 | 有序行为 |
|---|---|
| 09:00 | 两个市场开市，然后唤醒全部企业 |
| 09:00-18:59 | 执行事件驱动决策并连续撮合 |
| 19:00 | 完成到期作业和到货；关闭两个订单簿；执行消费者购买 |
| 19:00-19:29 | 只清空关市前已经承诺的作业和到货 |
| 19:30 | 要求订单、作业和到货全部清空；处理过期；写入快照 |

Scheduler 对同一分钟的系统事件使用显式优先级：

```text
作业/到货完成 -> 关市 -> 消费者购买 -> 日结
```

因此，零售商在 19:00 准时收到的商品可以参与当日消费者购买。18:59 的成交要到
19:29 才到货，无法参与 19:00 消费，但会在 19:30 快照前完成。19:00 及之后不再
接受企业决策。

`RuntimeSpec` 会校验日结时间足以覆盖最后一个命令分钟开始的最长作业或到货。

## 连续现货市场

每种商品拥有一个 `MarketState`，两个订单簿同时开关。V4 只提供普通 DAY 限价单。

### 资产冻结

- 一条 `set_quote_ladder` 命令为一个产品和方向定义零至三个价格互异的目标档位。每档
  数量和价格只有在校验为正数且都是 `0.0001` 整数倍后，才能越过引擎执行边界。非法
  原始命令会在创建市场事务前被拒绝，不会四舍五入。
- 买单从可用现金中移出按四位小数半偶舍入后的
  `remaining_quantity * limit_price`，存入 `BuyOrder`。
- 卖单从可用库存中移出准确的 FEFO 批次，存入 `SellOrder`。
- 尚未完成的生产、待到货和已被其他卖单冻结的批次都不可用。
- 所有待变化旧档与目标档都在一个事务中暂存。释放可复用的旧冻结后，全部目标买档
  名义金额或目标卖档数量仍必须获得真实担保；否则原阶梯及全部冻结保持不变。系统
  不会逐档提交，也不会在成交时静默裁剪数量。

企业私有观察会分别报告可用资产与冻结资产，因此 Agent 能看到完整经济所有权，同时
同一资产不能支持两次承诺。

### 撮合

只要 `best_bid >= best_ask`，进入订单会持续撮合：

1. 更优价格优先；
2. 同价按照持久化的 `priority_sequence` 排序；
3. 成交价取订单簿中 maker 订单的限价；
4. 成交量取双方剩余数量的较小值；
5. 能继续全额担保且舍入后非零的未成交部分保留原优先级；舍入尘埃或无法继续全额
   担保的余量会被自动撤回。

部分成交描述的是双方数量不相等，而不是担保不足；每个剩余单位仍然全额担保。买单
以低于自身限价成交时，未使用的价差资金立即回到可用现金。在统一四位精度下，独立
舍入的成交额与剩余冻结额可能相差一个最小单位；此边界只撤回余量，不回滚已完成成交。

报价阶梯表达目标状态。目标买档必须按价格从高到低提交，目标卖档必须按价格从低到高
提交；顺序错误会被拒绝。对账先保留价格和数量都完全相同的档位，再 Replace 剩余
同价档位；其余旧档与目标档按本侧价格优先顺序配对 Replace，无法配对的旧档 Cancel，
无法配对的目标档 Place。

`levels` 为空会 Cancel 对应产品和方向的完整阶梯。完全相同的档位保留订单 ID、到达
时间和优先级；每个 Replace 或 Place 档位都是拥有新身份和新优先级的独立订单。新档
从最优价到最差价依次进入撮合器，因此立即成交顺序确定。

由于命令不提供档位身份，“改价”和“删除后新增”的意图在观察上无法区分，两者都会
失去旧优先级；确定性配对在不要求 Agent 管理订单 ID 的前提下给出可审计结果。任一
校验、自成交或担保检查失败都会丢弃完整暂存事务。19:00 关市会释放全部未成交担保。

### 成交与到货

一次成交的状态流为：

```text
买单冻结资金支付成交额
卖方可用现金立即增加
价差资金退回买方
卖方批次成为买方所有的一条 PendingDelivery
30 分钟后批次进入买方可用库存
```

`PendingDelivery` 是强制执行提前期和精确 Replay 所需的最小状态，而不是物流聚合：
系统没有手动发货、托管、路线、承运商、运费、运力、延迟、损耗或失败转换。计划完成
要么在 `arrives_at` 恰好发生一次，要么触发 Runtime 不变量失败。

## 物理作业

`ProductionJob` 和 `TransformationJob` 是强类型异步承诺。启动作业时会：

- 校验角色、当日产能、资源空闲、现金和输入库存；
- 立即消耗现金，加工还会立即消耗输入库存；
- 记录恰好 30 个虚拟分钟后的完成事件；
- 直到完成创建新的易过期库存批次时，才暴露任何产出。

每家公司同时最多有一项物理作业。资源锁不会阻塞报价阶梯更新、零售定价或等待。
当日已用产能与当前作业分别记录，因此作业完成不会恢复当日产能。

## 决策与确定性并发

除物理后果外，命令本身没有模拟耗时。Runtime 通过每家公司每分钟最多一次决策的
节流和每日每家公司 25 Turn 的硬上限，避免零时间循环。每个 `AgentTurn` 都包含当日
Turn 序号和上限；触达上限时写入一条不改变经济状态的 `TURN_LIMIT_REACHED` Journal
记录。此后的每个因果 Wake 不再调用模型，但都会连同强类型信号写成
`AGENT_WAKE_SUPPRESSED` 审计步骤，而不是静默丢弃。

同一分钟唤醒的 Agent 观察同一个基础 `state_version`。推理并发执行，命令则按一个
完整的确定性排列应用：

```text
sort_key = SHA256(seed | absolute_minute | company_id)
```

产生的全局 `apply_sequence` 写入 Journal，表示命令处理顺序。命令应用时，每个 Place
或 Replace 档位按照目标价格从最优到最差获得独立、持久化的订单优先序号；未变化
档位保留原序号。真实响应延迟、重试和 Provider 负载只用于审计，不参与撮合。

稀疏决策由进程内 `AgentAttention` 模块负责。成功的 `wait` 可以设置最多三个 Agent
可见的 `best_bid` / `best_ask` 阈值 Alert，多个条件固定为 OR，并可指定一个绝对兜底
复查时间。显式时间必须在当日后续营业时间内，且最多等待 120 分钟；省略时默认在
120 分钟后复查，但若已经跨过关市则当天不再安排复查。重复、不可见或提交时已经为真
的 Alert 会使整条命令被拒绝，且不改变经济状态。

Alert 为一次性。系统只在同一分钟所有 seed 排序命令提交完成后，根据最终订单簿判断，
并在下一分钟唤醒企业。自有成交、作业完成和到货属于重要唤醒；普通订单簿变化不广播，
挂单也没有独立的轮询定时器。

## Agent 投影与信息边界

引擎构造企业私有的 `AgentTurn`，而不是暴露 `EconomyState`。除可用资产和事件外，
它还包含：

- 企业自己的 `open_orders`，每张订单都包含同价 FIFO 队列前方的当前未成交总量；
- 匿名 `order_books`：全部聚合价位及其数量、订单数、最近成交价和当日成交量；
- `reserved_cash`、`marked_surplus` 与 `inventory_expiry`；库存到期桶分别列出可用现货
  与卖单预留现货；
- `pending_deliveries`，包含准确到达时间和数量守恒的到期日分桶；
- `active_operation` 与权威的当日作业状态；
- 当日 Turn 序号与硬上限。

Provider Adapter 会额外生成一个强类型 `decision_constraints` 投影，其中显式包含
运行时限以及派生的已用/剩余作业产能。它在每次请求时从 `AgentTurn` 重建，从不持有
经济状态。

`marked_surplus` 将可用现金、买单预留现金、可用与卖单预留库存、在途交割和当前作业的
保证产出统一按不可变产品参考价值计值，再减去企业的 Episode 初始现金。因此，同一资产
在可用、预留、在途和已完成状态之间迁移不会制造虚假盈亏。`inventory_expiry` 只覆盖现货；
在途交割继续使用自身的到期分桶，在制品则只在作业完成后进入到期分桶。

其他企业的身份、资产、订单、记忆和 trace 均不可见。自然语言推理没有约束力；只有
通过校验的结构化命令能够改变经济状态。

## 记忆、持久化与 Replay

每家公司拥有自己的 token 预算 `ConversationMemory`。最近的完整
Turn/Command/Outcome 循环保留原文，更早的完整循环压缩为确定性摘要。记忆没有七天
截断，也永远不能替代当前权威事实。

不可变 Journal 记录企业 Turn 和有序 System Step。`RunCheckpoint` 保存精确恢复
所需的全部状态，包括订单簿及冻结资产、作业、到货、Scheduler、已激活注意力计划、
企业私有记忆、序号计数器、事件和快照。每个计划都必须与来源 Wait Turn 及准确的兜底
唤醒匹配。每个稳定虚拟时间边界上，Journal 增量与 Checkpoint 替换在同一数据库事务
中提交。

Replay 使用相同 Runtime 和引擎，但不调用模型。观察哈希、命令或协议拒绝、Outcome、
`apply_sequence`、系统影响、事件、快照和最终得分都必须完全一致。

## Episode 评价标准

每个有效 Episode 只产生一个与本轮 seed 对应的分数。评价器针对 30 天、3 家零售商，
从本轮 seed 推导每天的潜在需求 `A`，并使用连续净增值上界 `(A + 14)^2 / 32`；全部
求和得到 `E_ref`，它不取自任何参评模型。九家企业总净值增量为 `E_raw`，归一化效率为
`E = clip(E_raw / E_ref, 0, 1)`。

评价器分别计算三个层级内部 3 家企业增长倍数的原始 Gini。其有限样本最大值为 `2/3`，
因此公平分为 `F = 1 - (G_farm + G_processor + G_retailer) / 2`。企业只要在任意日末
满足现金与参考价库存价值之和为零，就计为破产；若破产企业数为 `D`，则 `B = D / 9`。
最终分为：

```text
Score = 100 * E * sqrt(F * (1 - B))
```

`s9-enterprise-v2` 在公式中保留完整中间精度，只在公开的 `CompanyScore` 与
`ScoreCard` 边界把所有 Decimal 统一为四位小数。

经济结果不再触发额外资格门槛。Episode 不完整、技术失败、协议无效或 Replay 漂移时不出分。

## 核心不变量

1. 只有 `EconomyEngine` 可以改变经济状态。
2. 同一分钟批次内，每家公司最多提交一条命令。
3. 每张挂单都由唯一冻结的现金或库存全额担保。
4. 每家公司在每个产品和方向上最多有三个价格互异的活跃档位；一条阶梯命令要么提交
   全部变化，要么一个也不提交。
5. 每张存续订单的数量都为正数且对齐 `0.0001` 市场步长；Journal 中的原始命令只是
   审计证据，不是可执行状态。
6. 每张活跃订单都有独立、持久化的优先序号；一条命令的 `apply_sequence` 不会被复用
   为三张订单的优先序号。
7. 可用、冻结和待到货库存批次的 ID 在全局唯一。
8. 每家公司最多有一项当前作业；每笔成交在完成前恰有一条待到货。
9. 两个商品市场共享 Session 状态，并始终同时开关。
10. `[09:00, 19:00)` 以外不接受任何企业命令。
11. 19:30 日终快照前，订单簿、作业和待到货必须全部清空。
12. Provider 完成顺序永远不能改变经济应用顺序。
13. Journal 与 Checkpoint 才是 Replay 权威，Prompt 和 UI 投影都不是。
14. 注意力模块只读取 Agent 的匿名市场投影；观察者 UI 的完整订单簿不能唤醒 Agent，
    也不能改变经济状态。
15. 所有跨越领域边界的经济 Decimal 都规范为 `0.0001` 的整数倍。外部超精度输入直接
    拒绝；派生金额使用半偶舍入，派生实物数量向下取整，零价值结算会被原子拒绝。

## 明确不做的事情

V4 不模拟信用、卖空、远期合同、双边自然语言谈判、自然语言结算、运输决策、运输
风险、消费者 Agent 或复杂交易所订单类型。只有当新机制能够形成可衡量的策略选择时
才应加入，并且不能削弱上述结构化结算与 Replay 不变量。
